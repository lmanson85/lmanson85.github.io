> PROJECT_01 / DETECTION ENGINEERING

Insider Threat Canary

A lightweight Windows-based insider threat detection prototype using deception technology, file-system auditing, PowerShell automation, persistent logging, and real-time administrator alerts.

PowerShell Sysmon Windows Event Logs Event ID 4663 SMTP Task Scheduler CSV Logging

01 / EXECUTIVE SUMMARY

Detecting Threats From Inside

Insider threats present a unique security challenge because employees, contractors, or compromised accounts may already possess legitimate credentials and access to organizational systems.

I designed Insider Threat Canary as an early-warning system that uses deception technology to detect potentially unauthorized internal activity. A sensitive-looking decoy file containing fake credentials is placed within the environment and monitored for access.

Core concept: A legitimate user performing normal job responsibilities should have no reason to interact with the decoy. Access therefore creates a high-signal event that can be investigated.

02 / DECEPTION DESIGN

Building the Canary

The decoy was designed to resemble sensitive payroll information. I created an Excel file named:

Salary_Adjustments_Jan-Mar_2025.xlsx

The spreadsheet contained fake login credentials following a realistic organizational naming pattern and was marked as administrative information.

I then placed the file deep within a simulated HR and Finance directory structure:

C:\Users\Public\CompanyData\HR\Finance\Reports\Final\Payroll\2025\

The intent was to create a file that would be unlikely to be accessed accidentally during normal activity but attractive to someone deliberately exploring sensitive internal information.

04 / WINDOWS AUDITING

Generating the Detection Event

Windows file-system auditing was enabled for successful and failed access attempts. I then applied an audit rule to the directory containing the decoy.

auditpol /set /subcategory:"File System" /success:enable /failure:enable

When the monitored object was accessed, Windows generated Security Event ID 4663. Event Viewer could then be used to verify the affected object and associated account information.

05 / AUTOMATION

CanaryWatcher.ps1

I developed a PowerShell watcher that continuously queried recent Security log events and checked them for the exact decoy filename.

Event Monitoring

Queries Windows Security events for Event ID 4663 and searches event messages for the decoy filename.

User Identification

Extracts account information from the event so the alert identifies the user associated with the activity.

Persistent Logging

Writes event information to a local CSV file for later investigation and review.

Administrator Alerting

Generates an SMTP email containing the file, date and time, user, and computer associated with the detection.

06 / EVIDENCE

Creating an Investigation Trail

The watcher maintained a CSV log so detections were not dependent solely on email notifications or console output.

Timestamp EventRecordId User Computer FileName Event Message

This provided a persistent record containing information that could be reviewed during an investigation.

07 / ALERT MANAGEMENT

Reducing Alert Noise

During testing, repeated file activity could generate multiple alerts in a short period. I added cooldown logic to prevent the system from repeatedly emailing the administrator for the same burst of activity.

Alert cooldown: The watcher used a 30-second cooldown between email notifications while continuing to monitor activity.

08 / AVAILABILITY

Automated 24/7 Execution

The detection system was designed to operate without requiring the administrator to manually launch the PowerShell watcher.

I configured Windows Task Scheduler to run CanaryWatcher with elevated privileges, including startup and logon triggers and automatic restart behavior if the task failed.

Startup Trigger

Starts monitoring when the system starts.

Logon Trigger

Provides an additional trigger when the user logs on.

Highest Privileges

Allows the watcher to access the security information required for monitoring.

Failure Recovery

Task Scheduler was configured to retry the task if execution failed.

09 / TROUBLESHOOTING

Testing the Entire Detection Chain

Building the detection was only part of the project. Testing exposed issues that required troubleshooting across the alerting workflow.

Excessive Alerts

Repeated activity produced too many notifications. I refined the monitored behavior and implemented cooldown logic to reduce unnecessary alerting.

Antivirus Interference

AVG interfered with execution of the PowerShell watcher. I identified the conflict and added the script location to the appropriate antivirus exception list.

Key lesson: Seeing the expected security event was not enough. The complete workflow had to be validated from detection through logging and administrator notification.

10 / TESTING & RESULTS

Validation

I tested both expected normal behavior and deliberate access to the canary to determine whether the prototype could distinguish between routine activity and interaction with the decoy.

✓ Detection Decoy access generated the expected security event.
✓ Alerting Email notification triggered when the decoy was accessed.
✓ Normal Activity Normal testing did not generate false-positive alerts.

11 / OUTCOME

What I Built

The final prototype demonstrated a complete insider-threat detection workflow: a realistic decoy, Windows auditing, automated event monitoring, persistent logging, administrator notification, and unattended execution.

Future improvement: Expand the concept across additional decoy files and folders and incorporate role-based alerting to make detections more contextual within larger environments.
